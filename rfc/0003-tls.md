# 0003: TLS termination and HTTPS upstreams

| Status | Date | PR | Release |
|---|---|---|---|
| accepted | 2026-10-27 | #18 | v0.3.0 |

> Terminate TLS on the listener (with ALPN for HTTP/2) and speak TLS to
> `https://` upstreams, with the handshake bounded so it does not become
> the cheapest way to burn the gateway's CPU.

## Problem

Dvarapala only listens in cleartext and only proxies to `http://`
upstreams (`UpstreamError::Unsupported`). Real deployments need HTTPS on
the edge, so today they put another TLS terminator in front, which then
sees the attack first and hides the peer address behind it.

HTTP/2 from browsers needs TLS with ALPN, and gRPC over the internet
(RFC 0004) and HTTP/3 (RFC 0006) both build on this RFC.

The TLS handshake is also an attack surface. A full handshake costs the
server one asymmetric signature (about 50 to 100 us of CPU for ECDSA P-256,
more for RSA 2048), while the client can open connections and abandon them
for almost nothing. A TLS listener without limits turns a modest connection
flood into CPU exhaustion.

## Proposal

- `[tls]` with a certificate chain and key in PEM turns the listener into
  HTTPS. ALPN offers `h2` and `http/1.1`; hyper serves whichever is chosen.
  Without `[tls]` nothing changes.
- TLS 1.2 and 1.3 only, rustls defaults for cipher suites, no
  renegotiation. Session resumption (tickets with a random key per process,
  rotated by rustls) cuts the cost of returning clients.
- Handshake limits, on by default:
  - `tls.handshake_timeout` (default `10s`): a connection that has not
    finished the handshake by then is closed.
  - `tls.max_handshakes` (default `1024`): handshakes in progress at once.
    Over it, new connections are closed before any crypto. Connections that
    finished the handshake do not count.
- `SIGHUP` reloads the certificate and key. A reload that fails to parse
  keeps the old pair and logs the error, so a bad file never takes the
  listener down. Open connections keep their session.
- One certificate per listener. SNI selection between several certificates
  is a later RFC if anyone needs it.
- `https://` upstreams: the proxy verifies the upstream certificate against
  the system roots, or against `upstream_tls.ca_file` when set. There is no
  switch to turn verification off; a self-signed upstream gets its CA in
  `ca_file`. `upstream_tls.server_name` overrides the name checked and sent
  in SNI (default: the upstream host).
- The client key and rate limit are unchanged: TLS adds no identity.
  TLS fingerprints (JA4) belong to the challenges RFC.
- Cargo feature `tls` on the `proxy` crate and on the binary, on by default
  in the binary. A build without it rejects `[tls]` and `https://` at start
  instead of ignoring them.

### Domain

| Crate / module | Responsibility |
|---|---|
| `crates/proxy/src/tls/acceptor.rs` | rustls server config, ALPN, handshake timeout and concurrency limit |
| `crates/proxy/src/tls/reload.rs` | load and swap the certificate pair, keep the old one on error |
| `crates/proxy/src/tls/client.rs` | upstream connector: roots, `ca_file`, `server_name` |
| `crates/proxy/src/server.rs` | accept loop takes a plain or TLS stream |
| `crates/proxy/src/reverse.rs` | accepts `https://`, picks the connector |
| `crates/dvarapala/src/config.rs` | `[tls]` and `[upstream_tls]` sections |
| `crates/dvarapala/src/main.rs` | `SIGHUP` handler calls reload |

The engine is untouched.

### Configuration

| Key | Default | |
|---|---|---|
| `tls.cert` | none | PEM certificate chain, leaf first. Unset: cleartext listener |
| `tls.key` | none | PEM private key (PKCS#8, PKCS#1 or SEC1). Required with `tls.cert` |
| `tls.handshake_timeout` | `10s` | Close connections still handshaking after this |
| `tls.max_handshakes` | `1024` | Handshakes in progress at once; over it, close before crypto |
| `upstream_tls.ca_file` | none | PEM roots for `https://` upstreams instead of the system store |
| `upstream_tls.server_name` | upstream host | Name verified and sent in SNI |

### Logs and metrics

| | |
|---|---|
| `dvarapala_tls_handshakes_total{result}` | `ok`, `failed`, `timeout`, `rejected` (over `max_handshakes`) |
| `dvarapala_tls_handshakes_in_progress` | gauge, compare with `max_handshakes` |
| `dvarapala_tls_resumed_total` | handshakes resumed from a ticket |
| `dvarapala_tls_cert_expiry_timestamp_seconds` | Unix time the leaf expires; alert on `... - time() < 14 * 86400` |
| `msg="tls reloaded"` / `msg="tls reload failed"` | `SIGHUP` outcome, with the error |
| `msg="handshake limit reached"` | sampled, at most once per second |

## Implementation notes

Found while building, folded back from the PRs:

- Case 4 sends plaintext HTTP instead of a TLS 1.1 ClientHello: rustls has
  no TLS 1.1 client to test with, and only offers 1.2 and 1.3 on the
  server side.
- Cases 8 and 9 call `Tls::reload` directly; the binary's `SIGHUP` handler
  only calls it, and was checked by hand.
- Integration tests assert behavior (closed, accepted, which certificate);
  the `footprint` job checks the handshake counter on a real binary.
- The expiry metric is an absolute timestamp
  (`dvarapala_tls_cert_expiry_timestamp_seconds`): a "seconds left" gauge
  set at load time would go stale between reloads.
- The expiry is read with a minimal DER walk (no X.509 crate), fuzzed with
  the `pem` target.
- The handshake runs in the connection's task, so a slow handshake never
  blocks the accept loop. `max_handshakes = 0` is a config error.
- The root store loads only for `https://` upstreams, so a cleartext
  upstream costs no memory for roots.
- `ReverseProxy::new` still refuses `https://`; `ReverseProxy::with_tls`
  takes the upstream TLS settings. `serve_tls` sits next to `serve`.
- CI also lints and tests the binary with `--no-default-features`.
- Case 19 (dev machine, both sides of a TLS 1.3 handshake with ECDSA
  P-256 in memory): about 260 us per full handshake.

## Alternatives

| Option | Why not |
|---|---|
| Leave TLS to a terminator in front | the terminator absorbs the flood and hides the peer, which is the job dvarapala is for |
| OpenSSL (`native-tls`, `openssl`) | C dependency, harder static musl builds, larger binary |
| rustls with `aws-lc-rs` (its default provider) | needs cmake and a C toolchain per target, larger binary; `ring` is enough for TLS 1.2 and 1.3 |
| Bundled Mozilla roots (`webpki-roots`) | stale roots baked into the binary; upstreams are usually internal CAs anyway, which `ca_file` covers |
| ACME (automatic certificates) | useful, but a separate concern with its own state and network calls; a later RFC |
| A switch to skip upstream verification | fail closed: an unverified upstream is a man in the middle waiting to happen |
| Reload by watching the files | `SIGHUP` is explicit and works with every secret manager; watching races with partial writes |

## Security and resource limits

- The attacker controls the ClientHello and the timing. rustls parses it
  in safe Rust; the PEM loader (operator input) gets a fuzz target.
- CPU: at most `max_handshakes` handshakes run at once, each bounded by
  `handshake_timeout`. Rejection happens before any crypto, so an over-limit
  flood costs an accept and a close.
- Memory: one rustls connection state (a few tens of KB) per handshake in
  progress, so about 32 MB worst case at the default `max_handshakes`.
  Per-IP connection limits come with the L4 RFC.
- The private key stays in process memory only. Logs never print key
  material or PEM contents, only paths and errors.
- Ticket keys are random per process and never written to disk.
- Upstream verification cannot be turned off.

## Rollout

- **Rollout:** v0.3.0. No `[tls]` means the same cleartext listener as
  today, so upgrading changes nothing.
- **Off switch:** remove `[tls]`, or build without the `tls` feature.
