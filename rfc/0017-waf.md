# 0017: WAF with OWASP Coraza as a sidecar

| Status | Date | PR | Release |
|---|---|---|---|
| implemented | 2026-10-29 | #138 | v0.12.0 |

> An optional WAF stage in the reverse proxy sends each request that
> passed the rate limit, detection and the challenge to an external
> inspection agent over HAProxy's SPOE protocol (SPOP), and blocks on
> its answer. The agent we build against is `coraza-spoa`, OWASP
> Coraza with the OWASP Core Rule Set (CRS); any agent that answers the
> same message plugs in. No WAF engine is linked into dvarapala.

## Problem

Dvarapala stops volume: floods, scrapers, credential stuffing at rate.
It does not look inside a request that arrives at a normal rate:

- One `GET /search?q=' OR 1=1--` per minute passes every bucket, every
  detection window and every route. So do path traversal, remote file
  inclusion, scanner probes with new paths, and Log4Shell style header
  payloads.
- Operators who want that protection run a second proxy (ModSecurity in
  nginx, Coraza in Caddy or HAProxy) in front of or behind dvarapala: one
  more hop that parses HTTP, one more config, one more thing to scale
  during an attack.
- `[[routes]]` with `deny` covers known paths, not payloads. Writing
  payload rules by hand is the job the CRS already does, with about 4,800
  regression cases behind it.

## Proposal

- A `[waf]` section turns on a stage between the challenge and the proxy.
  Requests that the earlier stages refused never reach it, so the
  expensive inspection runs only on traffic that is already within the
  limits.
- The stage is a client. Dvarapala speaks SPOP 2.0 (HAProxy's
  `doc/SPOE.txt`) to an agent at `waf.endpoint`, a TCP address or a Unix
  socket, usually a sidecar in the same pod or on the same host. Per
  request it sends one `NOTIFY` with the `coraza-req` message and reads
  the agent's `ACK`. The WAF engine, the rules and their reloads live in
  the agent.
- The agent we build and test against is `coraza-spoa` (corazawaf,
  Apache-2.0, released monthly, images for linux/amd64 and linux/arm64 at
  `ghcr.io/corazawaf/coraza-spoa`, a Helm chart in `corazawaf/charts`).
  It embeds Coraza and the CRS, reads SecLang directives per
  application from its YAML, reloads them on `SIGHUP` or a ConfigMap
  change, and exports its own Prometheus metrics.
- Pluggable at two levels. Rules: anything SecLang, in the agent's
  config, with no dvarapala release in the loop. Engine: any agent that
  accepts the `coraza-req` message below and sets the `action` and
  `status` variables. A different message shape (for example the
  ModSecurity SPOA from HAProxy's contrib) is a later RFC, not a key here.
- `mode = "observe"` (the default) sends, logs and counts, and always
  forwards; `"enforce"` answers the agent's status, as detection does:
  watch first, then enforce. The agent keeps `SecRuleEngine On`, so
  `waf.mode` is the one switch that decides blocking.
- Phases 1 (headers) and 2 (body) only. The request body is buffered up
  to `max_body` and sent with the headers; a larger body is refused
  (`413`) or sent without its body (`body_limit_action`). Response
  inspection (`coraza-res`) is out of scope: it needs the whole response
  buffered and adds latency to every byte.
- Failure policy: an agent that is down, too slow (`waf.timeout`) or
  answers garbage fails closed in `enforce`, with `503`, as every
  protection stage does. `waf.on_error = "pass"` opts into fail open,
  counted and logged. In `observe` an error always passes.
- Connections: a pool of at most `max_concurrent` connections, one
  `NOTIFY` in flight on each (no pipelining, no async capability), reused
  across requests. A request waits for a free connection within the same
  `timeout`. A connection that errors or gets `DISCONNECT` is dropped and
  redialed on demand.
- Skips: routes can turn the WAF off (`waf = false` in `[[routes]]`),
  for example for a gRPC or upload endpoint the CRS does not fit.
- `SIGHUP` and `POST /reload` (RFC 0014) apply the `[waf]` keys; the
  pool is rebuilt when `endpoint` changes. Rule changes reload in the
  agent.
- `dvarapala replay` (RFC 0016) sends to the agent too when `[waf]` is
  enabled, so a CRS paranoia level can be tried on yesterday's log before
  enforcing it. The log has no bodies, so replay covers phase 1 and the
  query string only.
- Build feature `waf` in `l7`, in the binary's default features. It adds
  a frame codec and a client over the tokio already linked, no new
  dependency, so the binary size and the RFC 0001 idle budget stay as
  they are.

### Usage

A pod with dvarapala and the agent, sharing a Unix socket (full manifest
in `examples/waf/`):

```yaml
containers:
  - name: dvarapala
    image: ghcr.io/franzramadhan/dvarapala:<version>
    volumeMounts: [{ name: spoa, mountPath: /run/spoa }]
  - name: coraza
    image: ghcr.io/corazawaf/coraza-spoa:<version>
    args: ["-config", "/etc/coraza-spoa/config.yaml", "-autoreload"]
    volumeMounts:
      - { name: spoa, mountPath: /run/spoa }
      - { name: coraza-config, mountPath: /etc/coraza-spoa }
volumes:
  - { name: spoa, emptyDir: {} }
  - { name: coraza-config, configMap: { name: coraza-spoa } }
```

`config.yaml` in the ConfigMap, the agent's side (the CRS is built in as
`@owasp_crs`):

```yaml
bind: unix:///run/spoa/coraza.sock
default_application: app
applications:
  - name: app
    directives: |
      Include @coraza.conf-recommended
      Include @crs-setup.conf.example
      SecRuleEngine On
      SecRequestBodyAccess On
      # own rules and CRS exclusions, before the CRS
      SecRule REQUEST_HEADERS:User-Agent "@contains sqlmap" \
        "id:190001,phase:1,deny,status:403,msg:'scanner'"
      SecRule REQUEST_URI "@beginsWith /cms/save" \
        "id:100001,phase:1,pass,nolog,ctl:ruleRemoveTargetByTag=attack-xss;ARGS:body"
      Include @owasp_crs/*.conf
    response_check: false
```

`dvarapala.toml`:

```toml
[waf]
enabled = true
mode = "observe"
endpoint = "unix:/run/spoa/coraza.sock"
app = "app"

[[routes]]
name = "uploads"
path = "/upload/"
waf = false
```

Tuning: watch `dvarapala_waf_rule_matches_total{rule}` and the
`waf match` lines (the agent's `coraza_rule_matches_total` has the
detail), add exclusions to the ConfigMap (the agent reloads it), try
the result with `dvarapala replay`, then set `mode = "enforce"` and send
`SIGHUP`. A stricter CRS paranoia level goes through the same loop.

Outside Kubernetes the agent runs as a systemd unit (`coraza-spoa`
ships one) or a second container, with `endpoint = "127.0.0.1:9000"`.

### Wire contract

The `coraza-req` message, arguments in this order (the agent reads `app`
first):

| Argument | SPOP type | Value |
|---|---|---|
| `app` | string | `waf.app` |
| `src-ip` | ipv4 / ipv6 | the client, from `X-Forwarded-For` only through `trusted_proxies` |
| `src-port` | uint32 | the client port (`0` behind a trusted proxy) |
| `dst-ip`, `dst-port` | ipv4 / ipv6, uint32 | the listener address |
| `method`, `path`, `query`, `version` | string, binary, binary, string | from the request line; `version` is `1.1`, `2.0` or `3.0` |
| `headers` | binary | `name: value\r\n` per header, as HAProxy's `req.hdrs` |
| `body` | binary | up to `max_body`, empty past it with `pass` |
| `exportRuleIDs` | boolean | `true`: the agent sets `rule_ids` |

Variables read from the `ACK` (transaction scope): `action` (any value
means blocked: `deny`, `drop`, `redirect`), `status` (answered when it
is 400 to 599, `403` otherwise), `ruleid` (the interrupting rule),
`rule_ids`, `anomaly_score`, `id` (logged). Unknown variables are
ignored, so an agent may add its own.

### Domain

| Crate / module | Responsibility |
|---|---|
| `crates/l7/src/waf/frame.rs` | SPOP frames: the varint, typed data, `HAPROXY-HELLO`, `NOTIFY`, `HAPROXY-DISCONNECT` out; `AGENT-HELLO`, `ACK`, `AGENT-DISCONNECT` in. Pure, no I/O |
| `crates/l7/src/waf/agent.rs` | the connection pool: dial (TCP or Unix), hello, one notify per connection, timeout, redial |
| `crates/l7/src/waf/layer.rs` | the `tower` layer: body buffering up to `max_body`, the message, observe or enforce, the failure policy |
| `crates/dvarapala/src/config/waf.rs` | `[waf]` keys and validation |

All behind `l7`'s `waf` feature. No new crate: the client is small and
only `l7` uses it.

### Configuration

| Key | Default | |
|---|---|---|
| `waf.enabled` | `false` | Turns the stage on |
| `waf.mode` | `"observe"` | `"observe"` logs and counts, `"enforce"` answers the agent's status |
| `waf.endpoint` | none | `host:port` or `unix:/path`; required with `enabled = true` |
| `waf.app` | `"default"` | The `app` argument: which agent application (rule set) inspects |
| `waf.timeout` | `"250ms"` | Wait for a connection, send, and read the answer, per request |
| `waf.on_error` | `"block"` | `enforce` only: `"block"` (`503`) or `"pass"` (forward, counted) |
| `waf.max_body` | `"16KiB"` | Request body sent at most; `0` sends headers only |
| `waf.body_limit_action` | `"reject"` | Over `max_body`: `"reject"` (`413`) or `"pass"` (sent without the body, counted) |
| `waf.max_concurrent` | `64` | Connections to the agent, so inspections at once |
| `routes[].waf` | `true` | `false` skips the WAF for the route |

The frame size proposed in the hello is `max_body + 16 KiB`; a request
whose headers do not fit in the rest is an error (failure policy).

### Logs and metrics

| | |
|---|---|
| `msg="waf match"` | the rule IDs, anomaly score, agent transaction ID, client, method, path and mode; at most one line per client per second |
| `msg="waf agent"` | connect and hello failures, `DISCONNECT` with its status and message; at most one line per second |
| `dvarapala_waf_requests_total{verdict}` | `pass`, `block`, `would_block` (observe), `skipped` (route), `error`, `body_over_limit` |
| `dvarapala_waf_errors_total{reason}` | `connect`, `timeout`, `protocol`, `disconnect` |
| `dvarapala_waf_rule_matches_total{rule}` | from `ruleid`, at most 256 distinct labels, then `other` |
| `dvarapala_waf_inspect_seconds` | histogram: the wait for a connection plus the round trip |

## Alternatives

| Option | Why not |
|---|---|
| Coraza in process over `libcoraza` (c-archive, cgo) | measured below: +14 MB binary, +11 MB idle RSS with the WAF off, and static musl only works with a startup workaround on Go runtime internals (golang/go#13492). It also ties every rule engine bump to a dvarapala release. The first draft of this RFC |
| `coraza-proxy-wasm` in an embedded Wasm runtime (`wasmtime`) | the Wasm runtime alone is larger than `libcoraza`, we would host the proxy-wasm ABI ourselves, TinyGo builds of Coraza are slower than native Go, and the last release is from 2025 |
| A pure Rust SecLang engine in process (`zentinel-modsec`) | the fastest and smallest in the spike, but one maintainer, first release 2026-02, and no sign it will be kept up; a WAF engine that goes quiet is a security problem we would inherit. Nothing stops someone wrapping it in an SPOA later |
| Envoy `ext_authz` (gRPC) as the protocol | needs `tonic` and `prost` in the binary, and no maintained Coraza server speaks it with bodies; SPOP has `coraza-spoa` from the Coraza project |
| Our own HTTP inspection API | we would also have to write and maintain the Go sidecar that answers it |
| `libmodsecurity` v3 (C++) | the reference SecLang engine, but it links PCRE2, libxml2, YAJL and more in C++; a static musl build for `FROM scratch` is a project of its own |
| Our own payload rules (libinjection port plus a few regexes) | rebuilds a small, worse CRS and leaves operators unable to use the rules they already know |
| A WAF proxy in front of or behind dvarapala (nginx with ModSecurity, Caddy with Coraza) | works today; a second HTTP hop with its own parser, timeouts and config. The sidecar only inspects, dvarapala stays the one proxy |

## Security and resource limits

- The agent sees every inspected request, bodies included. Over TCP the
  SPOP connection is plaintext: `endpoint` should be a Unix socket or
  loopback, and a non-loopback address logs a warning at start. TLS to
  the agent is out of scope (`coraza-spoa` has none).
- The agent's answers are parsed by `frame.rs` with the negotiated size
  as the bound; the fuzz target (case 2) covers the decoder. A rule ID
  label is capped at 256 values, so an agent cannot blow up the metrics.
- CPU moves to the agent: Coraza costs about 5 ms per KiB of body with
  the CRS (spike below), which is why `max_body` defaults to 16 KiB. An
  attacker at the per-client rate can keep the agent busy; requests then
  wait up to `timeout` and fail closed in `enforce`, never "send
  uninspected" unless `on_error = "pass"`. The stage runs after the rate
  limit, detection and the challenge, so a flood is shed before it costs
  an inspection (case 9). The agent's CPU limit is the operator's
  knob, separate from the proxy's.
- Memory in dvarapala: one buffered body per inspection in flight, at
  most `max_concurrent x max_body` (64 x 16 KiB = 1 MiB by default),
  plus one frame buffer per connection.
- Supply chain: no Go and no new crate in dvarapala. The agent image is
  the operator's choice; `examples/` pins it by version and digest.

## In-process spike (first draft, for the record)

A throwaway harness (not committed) linked `libcoraza` v1.8.0 (Coraza
v3.8.1) and loaded CRS v4.20.0 at paranoia 1 in blocking mode. Every
build blocked SQLi and traversal in the query and XSS in a form body,
and passed an ordinary GET and a 16 KiB form POST. Latency is one
inspection on one core, p50; arm64, macOS and Linux musl in a container
gave the same numbers within 10 %.

| | Coraza | Coraza + `coraza-wasilibs` | `zentinel-modsec` 0.5 |
|---|---|---|---|
| Binary size added (stripped) | 14.1 MB | 21.3 MB | 2.4 MB |
| Idle RSS, WAF off (Linux) | 11 MB | 49 MB | 0 (not loaded) |
| RSS with the CRS loaded (Linux) | 51 MB | 126 MB | 23 MB (macOS) |
| CRS load time | 93 ms | 285 ms | 184 ms |
| GET, 10 headers | 0.78 ms | 1.06 ms | 0.65 ms |
| POST, 1 KiB form | 5.5 ms | 2.2 ms | 1.1 ms |
| POST, 4 KiB form | 19 ms | 4.6 ms | 2.0 ms |
| POST, 16 KiB form | 78 ms | 11 ms | 4.9 ms |

What it showed: static musl breaks Go's `c-archive` at start and needs
`.init_array` surgery with `objcopy`; Coraza needs the `no_fs_access`
tag under `FROM scratch`; `coraza-wasilibs` pays its cost in `init()`
even with the WAF off. All of that stays in the agent's image with the
sidecar. `coraza-spoa` uses plain Coraza, so the first column is what
an inspection costs the agent, plus a loopback round trip.

## Rollout

- **Implementation:** the stack's tests layer adds the `waf` CI job
  (case 12, `coraza-spoa` as a service container) with a skip guard, and
  adds it to the required checks.
- **Release:** v0.12.0; the `waf` feature is in the default build and
  the image. `[waf]` off by default, `mode = "observe"` once enabled.
  `examples/waf/` ships the pod manifest for a plain Kubernetes cluster
  (tested on a local Kubernetes cluster), the agent ConfigMap and a compose file. `CREDITS.md`
  credits OWASP Coraza, `coraza-spoa` and the OWASP CRS, linked from the
  README and the site.
- **Off switch:** `waf.enabled = false`, or `mode = "observe"`, or
  `waf = false` on a route, all applied by `SIGHUP`. Stopping the agent
  with `on_error = "block"` fails closed: switch to `observe` first.

## Implementation notes

Found while building:

- Case 12 runs in the existing `test` job: `coraza-spoa` is one more
  service container there, next to Redis and PostgreSQL, and its test
  fails in CI when `DVARAPALA_TEST_CORAZA` is unset. No new required
  job, so no skip guard and no ruleset change. The image's own config
  runs the CRS on `:9000`.
- The engine's client resolution is now `dvarapala_engine::client_ip`,
  which `client_key` calls too, so the agent sees the same client as
  the limiter.
- The binary always builds the WAF layer, off until a reload turns it
  on; a build without the `waf` feature has a pass-through stand-in and
  refuses `waf.enabled`. `[waf]` needs `mode = "reverse"`.
- Routes skip the WAF only where routes apply: inside the rate limiter,
  with `rate_limit.enabled`.
- gRPC requests are sent without their body: a stream may never end.
- `observe` never answers `413`: a body over `max_body` is sent without
  it, whatever `body_limit_action` says.
- With `body_limit_action = "pass"`, `body_over_limit` is counted next
  to the verdict of the inspection without the body.
- Reading the body is not bounded by `timeout`; the `[l4]` body timeout
  covers a slow client.
- The `waf match` line of case 4 is not asserted in a test.
- The socket: `coraza-spoa` creates it `0755` as its own user, so the
  agent must run as dvarapala's user (`10001` in the image).
  `examples/waf/` does that, with `fsGroup` in Kubernetes and a tmpfs
  volume owned by `10001` in Compose, and uses `/run/coraza-spoa`. The
  agent removes a stale socket at start.
- Replay sends each line to the agent without a body, and the report
  adds the `dvarapala_waf_*` series.
- The fake agent must not `sleep(Duration::ZERO)`: tokio still waits for
  the next 1 ms timer tick.
- Case 13, Linux arm64 (4 vCPU VM), the bench next to the agent,
  criterion means: against the fake agent 39 us for the GET and 55 us
  for the 16 KiB form, under the 100 us bar. Through `coraza-spoa` 0.9.1
  with the CRS 4.25.0 at paranoia 1: 0.79 ms for the GET, 185 ms for a
  16 KiB form of about 600 short fields, 82 ms for a 16 KiB body of one
  token. The CRS cost grows with the fields, so `CONFIG.md` and
  `examples/waf.toml` say to size `timeout` for `max_body`.
